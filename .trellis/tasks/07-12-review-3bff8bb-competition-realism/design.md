# 审查设计

## 审查边界

本任务是只读审查。先建立仓库级结构地图，再以目标提交为中心扩展到必要的调用链、接口、配置、启动文件、测试和比赛约束。无关模块只记录职责，不进行逐行审阅。

## 证据层级

1. 目标提交差异与当前代码中的直接行为。
2. 仓库内消息定义、配置、启动文件、测试、README 和比赛说明。
3. 提交前后版本对比及必要的 Git 历史。
4. 通用 ROS 2、机器人硬件和比赛运行约束；若具体赛事条件无法从仓库确认，明确标为外部假设。

## 审查方法

- 对每个变更建立“输入 -> 状态/算法 -> 输出 -> 执行器或比赛行为”的链路。
- 检查接口契约、坐标系、单位、时序、QoS、超时、边界条件和故障恢复。
- 将发现分为阻断、严重、一般和验证缺口，并要求每项发现具备明确触发场景及现实影响。
- 对疑似问题进行反证：检查是否被上游约束、下游保护、启动配置或比赛流程消除。

## 输出结构

- 项目结构与比赛运行链路概览。
- 按严重程度排列的审查发现。
- 对提交整体比赛现实性的结论。
- 仿真、台架和实机验证建议，以及无法从仓库确认的残余假设。

## 兼容与回滚

本任务不修改产品代码，因此无运行时迁移或回滚。若后续要求修复，应另行确认修改范围，并保留目标提交前行为作为对照。
