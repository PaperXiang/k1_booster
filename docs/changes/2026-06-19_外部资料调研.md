## 1. 八一队 demo（同源于官方 Booster demo，固件 v1.5）

他们 README 自述的改动与遗留问题：

| 他们做的 | 我们的现状 | 处置 |
|---|---|---|
| RL 视觉踢球 `RLVisionKick` | 我们已有 | 跳过 |
| **Adjust 超时→chase 防卡死**（`adjust_timeout_secs`） | 我们没有，且同样有绕球死锁风险 | ✅ **已采纳**（默认关，见 `2026-06-19_adjust_timeout.md`） |
| 寻球读队友高置信度球位快速转向 | 我们已有（`k1_teammate_ball` + RobotFindBall 朝队友球位转） | 跳过（已具备） |
| 角色动态切换"始终≥1 守门员"，守门出击则最近队友补位 | 我们已有（`handleCooperation` 同规则 + 守门交接 `cmd=10+id`） | 跳过（已具备） |
| **持球队员 cost 特殊处理（不易被打断）** | 我们只有 chase 0.9 滞回 + `myCostRank` | 🔶 **提案**（见下，lead 黏滞，中风险） |
| 守门员视觉踢球出击/解围 | 我们守门用 `Chase`/`Kick` 解围 | 跳过（差别不大） |
| 守门员按球速预测落点提前防守（`ballVelX/Y`） | 我们刚**删掉**未完成的扑救挂载 | ⏸ **不采纳**：他们也标"有待改进"，且依赖球速预测+扑救，风险大、需大量调试 |
| 阻尼扑救（gk-damp 分支） | 同上 | ⏸ 不采纳（实验性，breaking 风险） |
| `set_up.sh` 一键配置（team_id/player_id/role/GC IP/iptables 防火墙） | 我们手改 config | 🔶 **提案**（纯运维脚本，低风险，但需按我们网段/流程定制） |
| 修复：二级比赛状态定义不符、角色切换、踢球连续性 | 需对照我们代码核查 | 🔶 **提案**：值得各花 10 分钟核对我们是否有同类 bug |

他们仍存在的问题（和我们高度重合，值得警惕）：浅色鞋误识别为球；卡门柱；**场地识别/坐标系鲁棒性极差**（=定位弱，与我们一致）。

### 提案 A：持球者 lead 黏滞（中风险，待审核）
思路：给"当前 lead/正在踢球的人"一个 cost 减免或切换迟滞，避免 lead 在两人间反复横跳导致都不上球。
- 落点：`handleCooperation` 的 `tmImLead` 判定（`brain.cpp:1079`）或 `updateCostToKick`。
- 风险：改团队分工核心，可能引入"该换不换"。**建议做成 config 开关、默认关**，单独成一次变更 + 报告，白天评审后再上。

### 提案 B：`set_up.sh`（低风险，运维）
- 价值：赛前快速设 team_id/player_id/role/GC IP，减少手改 config 出错。
- 注意：iptables 限网段是他们的安全偏好，按我们现场网络决定要不要；脚本要适配我们的 `config.yaml` 路径。
- 可随时做，不影响比赛逻辑。

## 2. B-Human（只取自包含思路，**明确不要其框架级 breaking changes**）

> 说明：未能抓取实时文档；以下为通用已知思路 + 我们 §12 已引用内容，落地前对照官方复核。

B-Human 是 SPL（NAO）强队，整套架构（Modules/Representations、CABSL 行为、UKF 世界模型）**很重，不可整搬**——正好符合你"不要 breaking changes"。可单点借鉴的自包含思路：

| 思路 | 与我们的契合 | 处置 |
|---|---|---|
| **复合场地特征全位姿定位**（中圈+中线、罚球点+禁区线 → 一次解出含朝向的全局位姿） | 直击我们最大短板"比赛中朝向不可纠"（§10.4）；团队 0618 已**试做** `SelfLocateCircle/Penalty` 但没实现导致崩溃、被我删除 | 🔶 **重点提案**（见下，中风险但价值最高） |
| 球模型多帧/队友融合 + 有效性标志 | 我们已有 Kalman 预测器 + 队友球共享 | 跳过（已具备） |
| 假设管理/sensor resetting（丢失后用近期观测重置粒子） | 我们入场用粒子滤波、比赛用几何校正 | ⏸ 低优先（属较大改动） |
| 搜索行为：转向"最可能球位" | 我们已有 find-ball + 朝队友球位转 | 跳过 |

### 提案 C：把 `SelfLocateCircle` / `SelfLocatePenalty` 真正做出来（中风险，最高价值）
- 这正是 §12 想做、但只连了 XML 没写实现导致崩溃的东西。**正确做法**（非 breaking）：
  1. 在 `brain_tree.h` 声明、`brain_tree.cpp` 实现这两个节点，`REGISTER_BUILDER` 注册；
  2. 复用 `locator->residual` 对全部地标做一致性校验（误检防护）；
  3. `max_theta_drift` 门限防 π 翻转；
  4. **默认不接入 `subtree_locate.xml`**（或用开关），先在 WebUI 看校正量是否合理，再灰度启用；
  5. 顺带修 §10.1 的 `(p1+p1)/2` 笔误。
- 价值：比赛中只要看到中圈或(罚球点+横线)即可纠正朝向，缓解打滑/陀螺漂移导致的"定位歪了就一直歪"。这也是八一队和我们共同的痛点。
- 风险：中。是定位逻辑，需离线/仿真充分验证；**建议单独一次变更 + 报告，白天评审**，不在夜间直接接入比赛树。
