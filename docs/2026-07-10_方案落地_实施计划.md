## 1. 代码现状事实（实现引用锚点，均已逐处核对）

2. **RLVisionKick** 节点（brain_tree.cpp:1395 onStart）进入即减速→`client->RLVisionKick(true)` 交 RL 接管；决策为其它值时被 `_while` 打断。
3. **开球等待**仅对**对方**开球生效：`updateKickoffMemory`（brain.cpp:1353-1387）置 `wait_for_opponent_kickoff`，解除条件 = `ballMoved()`（位移 > max(0.15×range, 0.3m)，:1356-1364）或 10s 超时。**我方开球没有对应的"触球前"状态**。
4. **我方开球窗口**已有：`handleSpecialStates`（brain.cpp:930）维护 `isKickingOff` / `isFreekickKickingOff`（KICKOFF_DURATION=10s）；`StrikerDecide` 里 kick 一次即清 `isFreekickKickingOff`（brain_tree.cpp:1115）。

7. **lead/assist**：按 cost 排名（brain.cpp:1150-1180），cost 计算 `updateCostToKick`（brain.cpp:1437）。
8. **通信报文**（team_communication_msg.h:7-27，定长 POD，100ms 单播）：已带 `playerRole / isAlive / isLead / ballDetected / ballLocationKnown / ballConfidence / ballRange / cost / ballPosToField / robotPoseToField / kickDir / cmdId / cmd`。**身份与定位共享的传输层已齐备，无需新增字段**。

## 2. 总体设计原则

- **一切新行为置于 config 开关后**，默认关闭；回退 = 关开关。
- **决定性算法代替协商**：所有机器人用相同输入（GC 包 + 通信状态）独立算出相同分工，不新增通信协议、不引入协商竞态。数据可信度排序：GC 包（全队同源）> 队友通信 > 本机感知。
- **槽位坐标参数化**：基于 `fieldDimensions` 与球位的几何表达式，同一套代码适配 adult/kid/robo_league。
- **不修改守门员既有行为**（GoalKeeperPlay / GoToGoalBlockingPosition 等原样保留，延续固定开球规格 §2）。
- 5v5/3v3 用同一套代码：槽位表按"存活 field player 数"截断，天然覆盖罚下缩编。

## 4. 任务2：身份判定逻辑（Phase 1）

### 4.1 目标不变式（来自方案"总体特殊强调"）

- I1 任意时刻场上**至多 1 名**守门员角色；I2 罚下/故障时角色轮转确定、全队一致；I3 不出现己方互相抢球（lead 唯一）；I4 GAME INITIAL/满员回到配置角色。

### 4.2 判定输入与 GK 身份源

- **GK 身份判定顺序**：① GC 旗标 `gcGoalkeeperIdx`（若 GC 配置了）→ ② 本机 `config->playerRole` / 队友 `tmStatus[i].role`。禁止按 ID/位置猜测现任 GK（延续固定开球规格 §1）。
- **轮转选举**（仅在"GK 缺位"时发生）允许用 ID 决定性选举**新** GK——这与"禁止用 ID 识别现任 GK"不冲突，且只依赖 GC penalty 数组（全队同源），各机独立计算结果必然一致。

### 4.3 规则表（重写 brain.cpp:1128-1147 的 switchRole 块 → 独立函数 `updateRoleAssignment()`）

| # | 条件（按序求值，命中即止） | 结果 |
|---|---|---|
| R0 | `gc_game_state==INITIAL`，或 READY/GET_READY 且满员（现状 :1145,:1247 保留） | 回配置角色 |
| R1 | 配置 GK（或 GC 旗标 GK）存活在场 | 他守门；**其他人绝不自封 GK** |
| R2 | GK 被罚下/红牌（以 GC penalty 为准） | 存活者中**最小 playerId** 接任 GK；原 GK 回场（penalty 清零）→ 接任者归还角色 |
| R3 | 场上仅剩 1 名我方存活 | 防守性场景（**仅限**对方 kickoff 等待期/对方任意球）→ goal_keeper；否则（含我方开球与普通比赛，**已确认**）→ striker，站位用 §5 的单人保底位（防守位与中圈之间） |
| R4 | 其余情况 | 维持当前角色 |
| R5 | 冲突消解：某时刻检测到 ≥2 个 role==goal_keeper（配置错误/交接竞态） | GC 旗标者保留；无旗标则小 ID 保留，其余强制 striker，并 `speak` 告警 |

- 现有 **GK 出击交接**（cmd=10+id，brain.cpp:1183-1243）保留，且交接产生的"临时 GK"记入黑板 `acting_goalie_id`，供 R1/R5 识别，避免下一 tick 被 R2 推翻。
- 防互抢球（I3）：现有 cost-lead 机制已覆盖；本次仅加**滞回**——lead 得主在 `ball_control_cost_threshold` 内附加 0.5s 保持期，防止两机 cost 接近时 lead 每 tick 抖动（brain.cpp:1163-1180 处加时间戳）。

### 4.4 配置

```yaml
strategy:
  role_assignment:
    enable: true              # false = 完全回到旧 switchRole 行为
    gk_takeover: true         # GK 罚下时是否选举替补 GK（R2）
    lead_hold_msecs: 500      # lead 滞回
```

### 4.5 验收用例（对齐固定开球规格 §10 的 1-10）

1) GK 罚下→最小 ID 存活者变 GK，全队各机计算一致（比对双机日志）；2) GK 回场→自动归还；3) 只剩 1 人在对方 kickoff 时=GK、我方 kickoff 时=striker；4) 满员 READY 回配置角色；5) 人为配置两个 GK→R5 消解成 1 个；6) 全程 rerun `debug/handleCooperation` 无角色振荡（1 分钟内切换 ≤2 次）。

## 5. 任务4：站位与战术（Phase 2，工作量最大）

### 5.0 通用机制：FormationPlanner（新文件 `src/brain/src/formation.cpp` + `include/formation.h`，纯函数可单测）

```
输入: scene, fieldDimensions, ballPosToField(可信), 存活 field players 的 {id, pose}（含本机, 升序 id）, 本机 id
输出: 本机 Pose2D 目标 + 该槽位语义名（kicker/receiver/blocker/cover/L1a/L1b/L2a/L2b/lone）
```

- **分配规则**：槽位表按场景给出 N 个槽（按重要性排序）；存活 field player 数 < N 时**从表尾截断**（天然实现 5v5→3v3→缩编）。id↔槽位映射默认升序对号；`assign_by_distance: true` 时用"贪心就近"（以各机上报位姿为输入，输入同源故各机结果一致）。
- **冻结与重算**：进入场景瞬间冻结分配；以下任一发生才重算——存活集合变化 / 球位移 > `replan_ball_move_threshold`(0.5m)（对应方案"开球前实时确认球是否动了"）/ 场景切换。重算带 0.5s 去抖。
- **前置条件**：`ball_location_known || tm_ball_pos_reliable` 才输出球相关槽位（方案：必须可信球位才执行站位规划）；不可信时回退各场景的静态保底位。
- **合法性夹紧**：场内收 0.5m；防守场景槽位不进本方禁区（GK 专属）；对方开球时我方槽位不入中圈（|pos|≥circleRadius+0.3）且在本方半场；任意球防守槽位距球 ≥1.5m。
- **载体**：新 BT 节点 `GoToFormationSlot(scene)`（内部走 `moveToPoseOnField2`，与现有节点一致），替换各场景对 `GoToReadyPosition`/`GoToFreekickPosition` 的引用；旧节点保留不删，config `strategy.formation.enable=false` 时 XML 分流回旧节点。

### 5.1 场景A：中场开球·进攻（图2；对齐固定开球规格）

- 角色链（**已确认**："下方球员"与"最下方球员"为同一人，即最下方、最靠右者）：**最上方球员开球（passer）→ 向 shooter 前方一点送小传球（领传，目标 = shooter 槽位 + 前向偏移 0.5m）→ shooter 接球主攻框**，两人链。与固定开球规格的映射：按存活 field player 升序 ID → [0]=shooter、[1]=passer、[2]=SUPPORT_1、[3]=SUPPORT_2（规格 §4 顺序不变，站位取本表）。
- 槽位（READY 阶段就位；y 号取"我方开球上方=左侧 y>0"，实际以确认表为准）：

| 槽位 | 参数化位置（待确认，推导自图2） | 语义 |
|---|---|---|
| passer | `(-0.3, +circleRadius×0.55)` 中圈上沿内 | 开球者，可入中圈 |
| shooter | `(-circleRadius×1.2, -2.2)` 最下方靠右（y<0 且 x 最靠前） | 接 passer 领传后主攻球门 |
| support_1 | `(-circleRadius×1.6, +0.6)` | 中场保护/二点球 |
| support_2 | `(-L/2+penaltyAreaLength+1.0, +0.5)` | 后场保护 |
| GK | 现状不变 |

- **时序**：READY 就位 → SET 静止 → PLAY 且 `isKickingOff`：passer 的 `CalcKickDir` 强制 `kickType="pass"`、`kickDir=atan2(shooter领传点−ball)`（新增 pass 类型，走既有 Kick 趟球，速度用 `soft_kickoff_speed` 档）；此期间 vision kick 被 §6 的 guard 抑制。球动（=触球完成）后 guard 解除，恢复 `StrikerDecide` 正常决策，shooter 因位置前压自然成为低 cost 者接管控球。
- **3v3**：截断为 GK + passer + shooter（support 槽删除）。
- **仅 1 人**：R3 → striker，槽位 = `(-L/2+penaltyAreaLength+1.0, 0)`~中圈之间的中点（方案：站防守球员位置和中圈之间）。
- **XML**：`game.xml` READY 段 `GoToReadyPosition` → `GoToFormationSlot scene="auto"`（内部按 `gc_is_kickoff_side` 选 A/B）。PLAY 段暂不加三路分流（趟球小传复用既有 StrikerPlay 链路 + kickDir/kickType 覆写即可，避免动 game.xml 主干；若后续实测需要专用 FixedKickoffPlay 子树，再按固定开球规格 §2.1 扩）。

| GK | 一直守门（现状） | 同左 |

- 开球动作与 A 相同：`kickType="pass"`、`kickDir=receiver 方向`、vision kick 被 guard 抑制、球动后恢复正常。
- **XML**：`subtree_striker_freekick.xml` 的 `GoToFreekickPosition side="attack"` → `GoToFormationSlot scene="freekick_attack"`。

### 5.4 场景E：边线球·防守（图6，三层人墙）

- 轴线 = **球 → 本方球门中心**。L1×2 距球 1.8m（≥1.5m 合规）横向间距 0.9m 成墙；L2×2 距球 3.5m 展宽 2.2m 堵侧漏；GK 现状。随球实时平移（GET_READY 内球动>0.5m 即重算，方案特别强调）。
- 3v3 截断：L1 居中 1 人 + L2 居中 1 人 + GK；1 人=GK。
- **XML**：`GoToFreekickPosition side="defense"` → `GoToFormationSlot scene="freekick_defense"`。
- 前置：可信球位（§5.0）；不可信时回退现状 `FindBall` 分支（subtree_striker_freekick.xml:16-18 已有，不动）。

### 5.5 场景F：全场射门/传球决策（**已确认裁剪到下期，本期不实施**，以下留作下期参考）

- `CalcKickDir`/`StrikerDecide` 增强：控球且角度可射时，用 `isFrontRangeClear(θ_goal±0.35rad, 3.0m)` + `data->getRobots()` 判"前方无对方球员干扰"→ **优先射门**（现状 kick）；有干扰 → 比较带球（kickDir 朝空当 `calcAvoidDir`）与传球（存活队友中选 `x` 更靠前且传球线无对手者，`kickType="pass"`）。`threatLevel()`（brain.cpp:3861）作为紧迫度输入。配 `strategy.smart_kick.enable`（默认 false）。

### 5.6 坐标敲定（**已确认：由实现方按场地尺寸直接敲定，无需另行确认流程**）

## 6. 任务1：开球后触球前禁用 vision kick（Phase 3）

### 6.1 kickoff_guard 状态

- 新增 `data->kickoffGuardActive`（+黑板 `kickoff_guard` 供 XML/WebUI），由 `handleSpecialStates` 维护：
  - **置位**：进入 `isKickingOff`（我方 kickoff）或 `isFreekickKickingOff`（我方任意球）时，锁存当时球位 `guardBallPos`（需 `ballDetected && confidence≥ballConfidenceThreshold && odom_calibrated`，即方案"定位和测距可信"；不可信则以首个可信帧锁存）。
  - **解除**：① `ballMoved`：`norm(ball.posToField − guardBallPos) > max(0.15×range, 0.3m)`（阈值口径与 brain.cpp:1356-1364 一致，但用 field 坐标以免自身移动误判）——即第一脚触球完成；② 10s 窗口自然到期（复用 KICKOFF_DURATION）；③ 比赛状态离开 PLAY。

### 6.2 三处抑制点

| 位置 | 改动 |
|---|---|
| StrikerDecide auto_visual_kick 条件（brain_tree.cpp:1067） | `&& !brain->data->kickoffGuardActive` |
| RLVisionKick::onStart（brain_tree.cpp:1395） | guard 期间直接返回 SUCCESS 不进 RL 模式（兜底，防其它路径触发） |
| CalcKickDir（brain_tree.cpp:906） | guard 期间 `kickType` 强制 `"pass"`（§5.1 的小传球），确保第一脚是趟球传递而非射门——对应规则"第一脚射门不算，接触后再射" |

- guard 解除后同 tick 恢复正常决策；对方开球时 guard 不置位（`wait_for_opponent_kickoff` 已覆盖对方场景）。

### 6.3 边线球 1.5m 合规

- `GoToFreekickPosition`/新槽位框架：attack 侧 kicker 占位距离 0.7→**1.5**（GET_READY/SET 阶段）；defense 侧现状 1.9 保持；§5.0 合法性夹紧统一保证"无论进攻还是防守"所有槽位距球 ≥1.5m。恢复 PLAY 后 kicker 正常接近踢球。

### 6.4 配置与验收

```yaml
strategy:
  kickoff_guard:
    enable: true
    ball_move_threshold: 0.3   # 与 0.15×range 取 max
```

验收：我方 kickoff/边线球全程 rerun 断言 `decision != 'auto_visual_kick'` 且无 `RLVisionKick(true)` 调用直至球位移越阈；第一脚 `kickType=="pass"`；超时 10s 后 guard 自动解除；对方开球流程行为无变化（回归）。
