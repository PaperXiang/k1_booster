## 0. 现有源码事实核对（实现前必读，所有规则以此为准）

下列事实均已逐处核对，决定了后续规则如何落地：

1. **队友通信已经携带角色**：`TeamCommunicationMsg.playerRole`（`team_communication_msg.h:13`，`1=striker / 2=goal_keeper`），
   接收端在 `brain_communication.cpp:520` 解码为 `data->tmStatus[i].role`（字符串 `"striker"`/`"goal_keeper"`，
   结构体见 `types.h:191`）。
   ⇒ **守门员识别跨机已经可用，无需新增通信角色字段**；§九中"通信没有 `player_role`"的兜底分支在本项目里不成立，
   只需在实现里直接读取 `tmStatus[i].role` 与本机 `config->playerRole`。
2. **导航目标是二维位姿 `x, y, theta`，没有 `z`**：`RobotClient::moveToPoseOnField / 2 / 3(double tx, double ty, double ttheta, …)`
   （`robot_client.h:66/81/94`），`Pose2D = {x, y, theta}`（`types.h:40`，`theta` 单位 rad，x 轴正向起逆时针为正）。
   `Point` 虽有 `x,y,z`（`types.h:48`），但那是**三维物体位置**（如球），**不是导航目标**。
   ⇒ 你提供的 `z` **不能**作为第三个空间坐标传给导航；只能解释为 `theta/yaw`，或仅留在配置里并在导航执行时安全忽略（见 §8）。
3. **本机不在 `tmStatus[]` 里**：`data->tmStatus[i]` 仅存**队友**（`handleCooperation` 中遍历时 `i==selfIdx` 跳过，
   `brain.cpp:977`）。构建在线列表时**必须显式把自己加入**，自身角色 / 号码取 `config->playerRole` / `config->playerId`
   （来源 `config.yaml` `game.player_role` / `game.player_id`）。`TMStatus` 不含显式 `playerId`，**数组下标 +1 即为该队友 playerId**。
4. **在线 / 存活判定**（沿用 `handleCooperation` `brain.cpp:976-993` 的口径）：队友 `i` 视为在线当且仅当
   `data->penalty[i] == PENALTY_NONE` **且** `msecsSince(tmStatus[i].timeLastCom) <= COM_TIMEOUT(5000ms)` **且** `tmStatus[i].isAlive`。
   替补（`SUBSTITUTE`）在 `brain_communication.cpp:511` 已被忽略。
5. **当前 PLAY 分流**（`game.xml:72-75`）：
   `StrikerPlay  _while="player_role=='striker'"` 与 `GoalKeeperPlay _while="player_role=='goal_keeper'"`
   两路互斥，挂在 `ReactiveSequence _while="gc_game_state=='PLAY'"` 下。新方案要在此基础上扩成**三路互斥**（见 §2）。
6. **现有动态机制必须能被关掉**：角色动态切换在 `handleCooperation`（`brain.cpp:1041-1060,1158-1165`）每 tick 改写 `player_role`；
   控球主力（lead）由 cost 排名在 `brain.cpp:1079-1092` 决定；视觉踢球开关 `strategy.enable_auto_visual_kick`。
   固定开球期间需要分别抑制这三者（对应 §7 的 `disable_dynamic_leader_selection` / `disable_auto_visual_kick`）。
7. **`myStrikerIDRank`（被禁止用于识别守门员）确实存在**：`brain.cpp:1071/1074`、`brain_data.h:148`。禁令针对得当。
8. **目前没有任何固定开球代码 / 节点 / 配置**（全库检索 `fixed_kickoff` / `FIXED_KICKOFF` / `shooter` / `passer` 均无命中）。
   本功能是全新增量：新增 `FixedKickoffPlay` 子树与若干节点、新增 config 段、（可选）新增分配报文。

## 1. 守门员识别规则

- 守门员**只能**通过角色字段判断：
  - 本机：`config->playerRole == "goal_keeper"`（即黑板 `player_role`）。
  - 队友：`data->tmStatus[i].role == "goal_keeper"`（已由通信填充，见 §0.1）。
- **禁止**用以下任何方式推测守门员：`player_id` 大小、在线 ID 排名、`myStrikerIDRank`、机器人位置、写死某 ID。
- 通信既已携带角色，**直接使用通信角色过滤守门员**；不需要"无角色兜底"逻辑。若未来确有未知角色的队友
  （`role == "not initialized"`，`types.h:192`），按 §9 处理：**未知角色不得进入固定角色分配**，且不得凭 ID 猜测其为守门员。

## 2. 守门员保持默认身份与行为（PLAY 三路分流）

固定开球模块**不得**对守门员做任何身份重分配 / 锁定。逐条约束：

1. 不修改守门员 `player_role`。
2. 不创建 `FIXED_KICKOFF_GOALKEEPER` 临时角色。
3. 不按 ID 排名选择 / 替换守门员。
4. 不向守门员施加 passer / shooter / support 角色锁。
5. 不改守门员 READY 站位。
6. 不改守门员 SET 行为。
7. 不改 `GoalKeeperPlay`。
8. 不改 `GoToGoalBlockingPosition` / `Chase` / `Adjust` / `Kick` 等现有守门行为。
9. 固定开球完成 / 失败 / 超时 / 禁用时，**无需恢复**守门员身份——因为从未修改过。
10. 不覆盖守门员的任何黑板角色字段或守门决策字段。

### 2.1 正确的 BT.CPP v4 XML（替换 `game.xml` 现有两路 PLAY 分流）

> ⚠ 语义陷阱：现有 `ReactiveSequence` 会**逐个**tick 子节点，`_while` 条件为假的子节点返回 `SKIPPED` 被跳过，
> 为真的子节点被执行。若把伪代码 `if/elif/else` 直译成「GK / 固定 / StrikerPlay」三个顺序子节点而**条件不互斥**，
> 当"固定"分支为真且返回 `SUCCESS` 后，`ReactiveSequence` 会继续 tick 到第三个 `StrikerPlay` 并**同帧再跑一次普通进攻**——
> 这就是执行语义错误。因此**三路 `_while` 必须严格互斥、互补**：非守门员分支显式排除 `goal_keeper`，普通进攻分支显式排除"已分配固定角色"。
> 用法、`&&`/`!=`/`==`/单引号字符串写法均沿用现有 `game.xml`（如 `:34 control_state==3 && (!go_manual)`、`:8 decision!='find'`）。

```xml
<!-- 替换 game.xml 中 gc_game_state=='PLAY' 那段的两路 SubTree -->
<ReactiveSequence _while="gc_game_state=='PLAY'" name="比赛">

    <!-- 1) 守门员: 永远走原 GoalKeeperPlay, 完全不受固定开球影响 -->
    <SubTree ID="GoalKeeperPlay" _autoremap="true"
             _while="player_role == 'goal_keeper'" />

    <!-- 2) 非守门员 且 固定开球生效 且 本机被分配了固定场上角色 -->
    <SubTree ID="FixedKickoffPlay" _autoremap="true"
             _while="player_role != 'goal_keeper' && fixed_kickoff_active && fixed_kickoff_role != 'none'" />

    <!-- 3) 其余非守门员(含固定开球未生效/未分配): 走原 StrikerPlay -->
    <SubTree ID="StrikerPlay" _autoremap="true"
             _while="player_role != 'goal_keeper' && !(fixed_kickoff_active && fixed_kickoff_role != 'none')" />

</ReactiveSequence>
```

依赖的黑板键（实现时新增，默认值要安全）：
- `fixed_kickoff_active`（bool，默认 false）：全队层是否进入固定开球（由 §5 的快照在 READY 置位）。
- `fixed_kickoff_role`（string，默认 `'none'`）：本机被分配到的固定角色，取值 `shooter / passer / support_1 / support_2 / none`。
  守门员**永远** `'none'`（分配时已排除，见 §3/§4）。

> `FixedKickoffPlay` 子树内部再用同样的「`ReactiveSequence` + 互斥 `_while`」按 `fixed_kickoff_role`
> 分到 shooter/passer/support_1/support_2 各自动作；具体动作节点待 §8 坐标提供后接入既有导航 / 踢球节点。

## 3. 固定开球场上球员列表（按现有结构构建）

只在**非守门员的在线机器人**中分配固定角色。落地到本项目数据结构（伪代码需按真实类型适配）：

```cpp
// online + 非守门员 → field_player_ids（含本机）
std::vector<int> field_player_ids;

// 1) 本机（不在 tmStatus 里，必须显式加入）
if (config->playerRole != "goal_keeper"
    && data->penalty[config->playerId - 1] == PENALTY_NONE
    && tree->getEntry<bool>("odom_calibrated")) {        // 本机"可用"判据, 对齐 tmImAlive
    field_player_ids.push_back(config->playerId);
}

// 2) 队友（下标 i → playerId = i+1）
for (int i = 0; i < HL_MAX_NUM_PLAYERS; ++i) {
    if (i == config->playerId - 1) continue;             // 跳过自己
    const auto& tm = data->tmStatus[i];
    const bool online = (data->penalty[i] == PENALTY_NONE)
                      && tm.isAlive
                      && msecsSince(tm.timeLastCom) <= COM_TIMEOUT;   // 5000ms
    if (!online) continue;
    if (tm.role == "goal_keeper") continue;              // 守门员排除
    if (tm.role == "not initialized") continue;          // 未知角色不参与(见 §9)
    field_player_ids.push_back(i + 1);
}

std::sort(field_player_ids.begin(), field_player_ids.end());
field_player_ids.erase(std::unique(field_player_ids.begin(), field_player_ids.end()),
                       field_player_ids.end());
```

要点：本机与队友用**同一口径**判在线；守门员、未知角色一律 `continue`；最终按 `player_id` 升序、去重。

## 4. 最终角色分配规则（按 `player_id` 升序）

排除所有 `player_role == "goal_keeper"` 后，对剩余在线 field players 按 `player_id` 从小到大排序，再分配：

| 在线 field player 数 | 分配 |
|---|---|
| **≥4** | `[0]=SHOOTER`，`[1]=PASSER`，`[2]=SUPPORT_1`，`[3]=SUPPORT_2`；第 5 名及以后 → 额外支援 / 普通防守，**不得抢占 shooter/passer** |
| **3** | `[0]=SHOOTER`，`[1]=PASSER`，`[2]=SUPPORT_1` |
| **2** | `[0]=SHOOTER`，`[1]=PASSER`（仍执行固定双人开球） |
| **<2** | `fixed_kickoff_active=false`，`fallback_to_normal_kickoff=true`，**直接进原普通开球逻辑** |

两人时的补充行为：
- 最小 ID = shooter，第二小 ID = passer；默认守门员继续原守门策略；不分配 support；
- passer 传球后进入配置指定的支援 / 回撤行为；
- shooter 明显失去接球机会时，尽快**释放固定射门权**、恢复普通协作。

`< 2` 时**禁止**：等待其他机器人上线 / 创建不完整角色映射 / 单机同时兼任 passer 与 shooter /
进入 `FIXED_DOWNWARD_PASS` / 进入 `FIXED_SHOOT`。

> 说明：上述 `SHOOTER/PASSER/SUPPORT_*` 是**场上职责**，写入本机黑板 `fixed_kickoff_role`；它们**不是** `player_role`，
> 不替换 striker/goal_keeper 身份（守门员根本不进此表）。

## 5. 角色冻结规则

- 角色映射在 **READY 阶段**基于**一次权威在线快照**生成并**冻结**（可挂在 `handleCooperation` 现有
  `gc_game_state=="READY"` 处理点附近，`brain.cpp:1158`；或新增等价钩子）。
- 冻结内容**只含**：shooter / passer / support_1 / support_2 / 其余 field player 的非抢球职责。**不含 goalkeeper**。
- PLAY 开始后：
  - 不因短暂丢包重新排序；
  - 不因 cost 变化更换 shooter；
  - 不因球位置变化更换 passer；
  - 不修改 goalkeeper；
  - **passer 或 shooter 掉线 → 终止固定开球，回退普通策略**；
  - **球发生第一脚移动后，禁止重新分配 passer / shooter**（"第一脚移动"判据可复用 `updateKickoffMemory`
    的 `ballMoved()` 阈值思路，`brain.cpp:1269-1275`）。

## 8. 坐标参数处理（关键：本项目导航是 `x, y, theta`）

具体固定开球坐标将在**代码编辑阶段由你提供**。在此之前：

- **不得**自行编造 shooter / passer / support 坐标；
- **不得**根据示意图猜测数值；
- **不得**把任何示例值当作最终配置；
- 配置中一律用**占位符**标记为"待提供"。

占位结构（先写占位符，收到后再填实数）：

```yaml
strategy:
  fixed_kickoff:
    positions:
      shooter:    { x: <待提供>, y: <待提供>, z: <待提供/见下> }
      passer:     { x: <待提供>, y: <待提供>, z: <待提供/见下> }
      support_1:  { x: <待提供>, y: <待提供>, z: <待提供/见下> }
      support_2:  { x: <待提供>, y: <待提供>, z: <待提供/见下> }
```

收到坐标后**必须先核对**：①参考坐标系；②单位（米 / 厘米 / 其他）；③是否全局场地坐标；
④`z` 的真实含义（高度 / 朝向 / 其他）；⑤现有导航目标用 `x,y,theta` 还是 `x,y,z`；⑥是否需按进攻半场镜像；
⑦是否在合法场地区域内；⑧是否与中圈 / 禁区 / 边线 / 规则冲突；⑨passer→球路径是否穿过 shooter；⑩support 是否挡固定传球线。

**本项目的明确结论（已核对，见 §0.2）**：现有导航接口是**二维位姿 `x, y, theta`**
（`moveToPoseOnField/2/3(tx, ty, ttheta, …)`，`Pose2D{x,y,theta}`），**没有 `z` 这个空间维度**。因此：

- 若你提供的 `z` 实际表示**高度**：**不得**强行传给二维导航；可保留在配置结构中、当前导航执行时**安全忽略**，并**记录警告**说明用途。
- 若你的 `z` 实际表示 **yaw / theta / 其他姿态**：按**本项目 `theta`（rad，x 轴正向起逆时针为正）**解释并映射到 `ttheta`，
  **不能**按常规三维坐标自行推断；必要时回到 `robot_client.h` 的接口签名确认。
- 站位下发统一走现有 `moveToPoseOnField2/3`（与 `GoToReadyPosition` `brain_tree.cpp:3324` / `GoToFreekickPosition` `:649` 一致）。

## 10. 测试要求（新增）

1. `role == "goal_keeper"` 的机器人不会进入 `field_player_ids`。
2. goalkeeper 的 `player_role` 在固定开球前后保持不变。
3. goalkeeper 始终执行原 `GoalKeeperPlay`。
4. 最小 ID 恰为 goalkeeper 时，该 ID 被排除，下一名 field player 成为 shooter。
5. 第二小 ID 是 goalkeeper 时，排序结果仍正确。
6. 2 名 field player + 1 名 goalkeeper 时，正确分配 shooter / passer。
7. 只有 1 名 field player 时，回退普通开球（`fixed_kickoff_active=false`）。
8. 队友角色未知（`not initialized`）时不会被误分配为固定角色。
9. 固定开球完成 / 中止不会改变 goalkeeper 的任何 Blackboard 状态。
10. 配置 `enabled:false` 时，所有角色 / 行为保持原逻辑（含 §0.6 三个动态机制不被抑制）。
11. 代码编辑阶段提供的坐标能被正确读取。
12. 坐标缺失 / 类型错误 / 越界 / 单位异常时安全回退。
13. `z` 不受当前接口支持时不会导致导航异常（被忽略或正确映射为 theta）。
14. 不同机器人对 goalkeeper 身份判断不一致时，固定开球**不**启动。
15. PLAY 三路分流互斥性：任意一帧只执行 GoalKeeperPlay / FixedKickoffPlay / StrikerPlay 之一，绝不同帧跑两路（防 §2.1 语义陷阱回归）。

---

## 11. 最终方案摘要（硬性结论）

- goalkeeper 通过 `player_role == "goal_keeper"` 判断（本机 `config->playerRole`，队友 `tmStatus[i].role`）。
- goalkeeper 从 fixed kickoff field player 排序中**排除**。
- **不锁定、不修改** goalkeeper。
- goalkeeper **始终**执行默认策略（原 `GoalKeeperPlay`）。
- field players 按 `player_id` **升序**分配。
- 最小 field player ID = **shooter**。
- 第二小 field player ID = **passer**。
- **两名** field players 即可执行固定开球。
- 少于两名 field players → **回退普通开球**。
- 实际坐标**由你在代码编辑阶段提供**。
- 收到坐标前**不得虚构**具体数值。
- 收到坐标后**必须先核对**坐标系、单位与导航接口；本项目导航为 `x, y, theta`（无空间 `z`），`z` 须解释为高度（忽略+警告）或 theta（映射）。
